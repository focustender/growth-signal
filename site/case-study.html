The finding that started it

From a 3,200-customer synthetic dataset modeled on Fireclay's own funnel language (interest → sample → project → purchase → repeat → advocacy), analyzed directly with Claude Code against a local SQLite store.

73%

of trade leads acquired at trade shows who request exactly one sample never advance to a project upload or purchase — more than double the stall rate of leads acquired through email capture (33%). The single strongest predictor of eventual purchase in this segment is requesting a second sample, which trade-show leads do at less than half the rate of the trade segment overall.

HubSpot ↔ Salesforce reconciliation

A live, config-driven reconciliation of both real accounts — not a mockup of one. The methodology is generic (analysis/crm-reconciliation/reconcile.py has no Fireclay-specific field names); the findings below are from actually running it.

Finding

100% lifecycle-stage disagreement

Of 85 contacts genuinely live in both systems, all 85 show HubSpot's lifecyclestage stuck at "lead" while Salesforce's Lead.Status already reads "Closed - Converted" — one mechanism (a field never written to after import), not scattered noise.

Experimentation: a real stop-and-redesign decision

Real analysis against real historical volume, not a simulated experiment result. The question asked before spending any runway: can the backlog's own proposed test actually work?

Finding

The test as specified can't work

A power analysis shows the backlog's Hypothesis 1 test (90-day holdout, 8pp scale threshold) needs 623 trade-show leads. The channel produces ~10/month — 62 months to get there. Checked whether a faster-arriving proxy metric would fix it; it doesn't, confirming a real population ceiling, not a fixable test design.

Read the findings →
Decision memo

Stop, learn, redesign

Kills the randomized-holdout design, not the hypothesis: full rollout, directional monitoring over two quarters, and an explicit reversal bar — the JD's own "scale, stop, or learn next" language, answered with an actual call instead of a backlog entry.

Reactivation: the mechanism, made real

The JD names "activation, education, nurture, reactivation" as the lifecycle side of the Trade Program. The backlog's reactivation hypothesis (Hypothesis 2 — the Trade Portal single-sample re-entry flow) couldn't be evaluated for a real conversion rate, since the prototype has no production traffic yet. So instead of leaving it there, this round tested whether the mechanism itself actually works against the live store — and it didn't, until a real bug was found and fixed.

Live systems check

A bug only a live test would catch

The three companion sample products backing the Sample Kit Builder had zero real inventory with a deny-oversell policy — meaning the reactivation prompt would have failed silently the moment a real lead clicked it, with no error anywhere a merchandising owner would notice.

Read the finding →
Fixed, live + in code

From console.log stub to a real cart action

Restocked all three SKUs live (verified via each API call's response, not assumed) and rebuilt the button's handler to resolve real variant IDs in Liquid and POST an actual /cart/add.js call, with honest success/error states in place of the old stub.
